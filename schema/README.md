# JSON-схема ответа

Задача **T-03** ([#12](https://github.com/tonclap/reuse-ideas-generator/issues/12)), роль 1 — Выдача. Волна 1: пишется **до первого
прогона**, запросов к модели не делает.

| Файл | Что это |
| --- | --- |
| [`response.schema.json`](response.schema.json) | схема ответа на одно фото |
| [`example_item_06.json`](example_item_06.json) | валидный пример: реюз применим, уточняющий вопрос не нужен |
| [`example_item_13.json`](example_item_13.json) | валидный пример: реюз **неприменим**, явный отказ |

## Как подключается

Файл — это **ровно то, что кладётся в `json_schema.schema`**, копипастой, без обёрток.
Поэтому в нём нет ни `$schema`, ни `$id`: строгий режим не принимает лишних ключевых слов,
и файл, который пришлось бы перед отправкой чистить, рано или поздно уедет от того, что
реально ушло в запрос.

```jsonc
"response_format": {
  "type": "json_schema",
  "json_schema": {
    "name": "reuse_ideas",
    "strict": true,
    "schema": { /* содержимое response.schema.json */ }
  }
}
```

Схема написана под **строгий режим**: у каждого объекта `additionalProperties: false`, а
`required` перечисляет **все** свойства без исключений. Отсюда же выбор формы для
необязательного — `"type": ["string", "null"]`, а не отсутствие поля: в строгом режиме поле
нельзя не прислать, можно только прислать `null`. Ключевых слов, которые строгий режим не
держит (`minItems`, `pattern`, `format`, `$ref`, `oneOf` и подобные), в схеме нет — счётные
ограничения («лучше две привязанные идеи, чем пять общих») живут в `description`, а не в
валидаторе.

Точная форма `response_format`, эндпоинт, заголовки и способ кодирования изображения — за
**T-02** ([#17](https://github.com/tonclap/reuse-ideas-generator/issues/17)): по [D-010](../COMMON_DECISION.md) structured outputs держит не модель, а связка
модель + провайдер-эндпоинт, и проверяется это на конкретном маршруте. Блок выше — форма,
описанная в документации OpenRouter, а не подтверждённый прогоном рецепт.

## Что уже проверено, а что нет

Проверено локально, без обращения к модели:

- схема — валидный JSON Schema, оба примера ей соответствуют;
- строгий режим: `additionalProperties: false` и полный `required` на всех трёх уровнях
  вложенности, неподдерживаемых ключевых слов нет;
- инварианты примеров: при `reuse_applicable: false` массив `ideas` пуст и
  `not_applicable_reason` заполнен; каждое `visible_detail` начинается дословной копией
  записи из `visible_details`.

**Не проверено:** ни один маршрут эту схему не принимал, ни одного ответа модели по ней не
существует. Оба примера **написаны руками** — это иллюстрация формы, а не выдача сервиса.
Пункт «маршрут из T-02 её принимает» из условия готовности T-03 **не закрыт** и закрыться
до T-02 не может, поэтому issue [#12](https://github.com/tonclap/reuse-ideas-generator/issues/12) остаётся открытой.

## Почему поля такие

Состав задан D-009 (reuse-only) и условием готовности T-03. Что стоит за формулировками:

- **`visible_details` отдельно от идей.** Модель сначала называет, что видит, и только потом
  опирается на это в идее. Главный риск, названный обеими разведками независимо, — идеи,
  общие для класса вещи; разнесение наблюдения и вывода даёт этот разрыв заметить.
- **`visible_detail` внутри идеи, дословной копией.** Пункт 1 критерия D-011 считается
  именно по этому полю. При наборе 100+ и двух прогонах на снимок (D-014) глазами (D-015)
  это 200+ оценок — форма выбрана так, чтобы связку можно было проверять машинально.
- **`reuse_applicable` + `not_applicable_reason` вместо пустого списка.** Пункт 3 критерия
  D-011 требует, чтобы на `item_10` (стройматериал) и `item_13` (расходник) сценарий был
  отброшен **явно**. Пустой массив идей молчит о причине и неотличим от сбоя.
- **`clarifying_question` и `uncertainty_note` — разные поля.** D-013 — «не всегда и не
  никогда»; эталоны T-05 считают лишний вопрос такой же ошибкой, как пропущенный. Вопрос —
  когда решающего в кадре нет физически; пометка — когда ответ дан, но держится на
  предположении. Один слитый флаг «не уверен» этой разницы не различает.
- **D-024 сидит в `description` шагов, а не в отдельном флаге.** Для `electronics` сценарии
  со вскрытием корпуса не выдаются вовсе — значит, запрещать надо на входе в поле, а не
  помечать на выходе. Оговорка: это точечный запрет по одной категории; нужен ли общий
  механизм — открытый вопрос D-028 ([#11](https://github.com/tonclap/reuse-ideas-generator/issues/11)), и схема его не предрешает.
- **`undetermined` в `category`.** Седьмой категорией не является: таксономия из шести
  значений заморожена до конца build (D-019). Это признание, что по кадру предмет не
  опознаётся, — случай `item_11`, где без ответа человека нельзя назвать даже категорию.

# TODO — путь до вердикта «прототип ✓»

> **Статус: черновик на ревью, 01.09.2026.** Разбивка работы на задачи, из которых после
> сверки заводятся issues. Решением ничего отсюда не является: решения живут только в
> [`COMMON_DECISION.md`](COMMON_DECISION.md), нерешённое — в
> [issues с меткой `ask`](../../issues?q=is%3Aissue+label%3Aask). Здесь только работа.

Финиш плана — не «сервис готов», а **проверенный вердикт по критерию D-011**: прототип
годен или нет. Сейчас `main.py` печатает пути и ничего не делает, а критерий ни разу не
проверялся реальным прогоном ([D-020](COMMON_DECISION.md) перенёс этот риск в build, а не
снял его).

**Вердикт берётся на полном наборе — 100+ фотографий** ([D-026](COMMON_DECISION.md)).
Пятнадцать снимков в `input/` — текущее состояние, а не мера: на них идёт калибровочный
прогон в волне 2, но засчитывается прогон на собранном наборе. Поэтому сбор набора стоит
в критическом пути, а не сбоку.

## Как читать

- **Одна задача = одна небольшая агентская сессия и одна роль** из
  [`ROLES.md`](ROLES.md). Задача, которой нужны две роли, разбита на две. Две задачи —
  T-08 и T-15 — в один заход не влезают, это отмечено прямо в них.
- **Готово, когда** — проверяемое условие, а не ощущение. Оно же идёт в тело issue.
- **Режим** — прямой push или PR, по [D-003](COMMON_DECISION.md): документы прямым push,
  код и конфигурация прогона через PR. Новые артефакты, которых в D-003 нет по имени
  (файл схемы, файл промпта), идут **через PR по умолчанию** — рабочая трактовка, в
  реестре не записана.
- Волны — это порядок, а не сроки. Внутри волны задачи **не блокируют друг друга**, но
  параллельными по людям не являются: роли 1 и 3 несут по две задачи в волне 1, и делает их
  один человек. Прежняя формулировка «не пересекаются по ролям» была неверна для всех волн,
  кроме нулевой.
- **Номера — идентификаторы, а не порядок.** T-04 стоит после T-07, потому что переехал в
  свою волну; перенумеровывать весь файл ради последовательности дороже, чем сохранить
  ссылки на задачи в issues и коммитах.

**Роль 3 — Данные (Григорий).** Прямой push (`research/`).
Гипотеза C4 из [explore](research/EXPLORE_tonclap.md): размеченный набор — единственный способ

Размечаются только эти пятнадцать: они разобраны поимённо в

реальных ответов, и если эталоны пишутся после них, три строки таблицы из пятнадцати
оказываются подогнанными под увиденное. Порядок задан явно, потому что обе задачи ведёт
один человек и разнести их некому.
**Осторожно:** исходные ярлыки владельца эталоном не считать — на `item_04` они уже соврали
(ждали изношенное покрытие, сковорода оказалась как новая).

### T-06 · Протокол судейства

**Роль 4 — Оценка и безопасность (Алексей).** Через PR, approve второго участника.
Не потому, что это код, а потому что протокол задаёт **содержание** критерия D-011:
формулировка подписана обоими через PR, а «что считать ссылкой на видимую деталь» решается
здесь. Пройти это в одиночку — переписать подписанное решение прямым push.
Судит человек глазами ([D-015](COMMON_DECISION.md)) — значит, нужна форма, а не вкус. Что
считается «ссылкой на видимую деталь», а что общими словами; что засчитывается за «пометку
неуверенности»; как отмечается отброшенный неприменимый сценарий. Три пункта критерия
[D-011](COMMON_DECISION.md) (ред. 2, порог ≥70%) превратить в размечаемые галочки.
Протокол обязан быть **быстрым**: на полном наборе по нему размечать 200+ ответов.
**Готово, когда:** протокол записан до прогона; двое, размечая один и тот же ответ по нему,
получают одинаковый результат; замерено, сколько секунд уходит на один ответ.
**Пример для сверки писать руками, а не брать из выдачи модели.** Прежняя формулировка
предлагала проверять протокол на ответе из T-04 — среди трёх его фото был `item_13`, один
из двух снимков, поимённо зашитых в пункт 3 критерия D-011. Инструмент измерения
настраивался бы на ответе по тому самому фото, которое им и меряют. Рукописный пример
ничем не хуже: сверяется согласие двух разметчиков, а не качество модели.

### T-07 · Источники и лицензии для расширения набора

**Роль 3 (Григорий).** Предложение → PR в `COMMON_DECISION.md`.
D-026 требует 100+ фотографий, включая взятые из интернета, — а это **чужие изображения**, и
вопрос лицензий за ними не закрыт (`TASK_DESC.md`, «Набор для проверки»). Задача — не собрать,

репозитория после [D-018](COMMON_DECISION.md).
**Готово, когда:** предложение на страницу с 2–3 вариантами источников и их лицензиями ушло
в PR по ритуалу [D-008](COMMON_DECISION.md). Это решение, а не работа, — значит, нужны обе подписи.
**Блокирует:** T-08. Пока лицензии не решены, каждый добавленный файл — необратимая
публикация чужого изображения.

### T-09 · Код прогона вместо заглушки

**Роль 1 (Григорий).** Через PR.
`main.py` читает `input/`, шлёт по маршруту из `config.yaml`, складывает сырые ответы в

### T-10а · Прогон на собранном наборе

**Роль 1 (Григорий).** Режим как у T-09/T-10 — через PR; кода задача при этом не меняет,
в PR идёт только `output/<run-id>/`.
Повторить прогон T-10 после того, как набор собран: те же промпт, схема и маршрут, два

**Зачем задача заведена.** Шапка этого файла говорит, что вердикт берётся на полном наборе,
но T-09 и T-10 работают с тем, что лежит в `input/` на момент написания кода, то есть с

кого: T-14 меряет по маршрутам цену и долю валидных ответов, а не складывает выдачу для
разметки. Вердикт опирался на прогон, которого никто не запускает.
**Готово, когда:** в `output/` лежит пара ответов на **каждое** фото собранного набора;
число фото совпадает с числом строк в `PHOTOSET_tonclap.md`; стоимость прогона записана.
**Зависит от:** T-08, T-10.

цена прогона перестаёт быть долями цента — считать до, а не после.
**Готово, когда:** по каждому маршруту есть стоимость прогона, время и доля ответов, прошедших
схему; один маршрут выбран по умолчанию и записан в `config.yaml`.
**Зависит от:** T-11, T-09.

### T-15 · Судейство и вердикт «прототип ✓ / ✗»

**Роль 4 (Алексей).** Через PR, approve второго участника.
Вердикт закрывает стадию — тот же класс события, что D-020 (закрытие explore), а тот
оформлялся решением с двумя подписями. По [D-022](COMMON_DECISION.md) тайбрейка нет:
объявить прототип годным или негодным в одиночку значит принять решение за двоих.
Разметить выдачу по протоколу T-06 и посчитать три пункта D-011 (ред. 2, ≥70%) **на полном
наборе**. Опорные 15 из T-05 идут первыми: расхождение разметки с эталоном показывает, что
протокол сырой, — это ловится до того, как размечены остальные.
**В одну сессию не влезет:** 100+ фото × 2 прогона = 200+ ответов. Резать партиями, число из
T-06 (секунд на ответ) даёт размер партии. Вердикт считается один раз, когда размечено всё.
**Готово, когда:** посчитаны все три пункта, вердикт записан с числами, а не оценочно; если
✗ — названо, какой именно пункт не взят; вердикт внесён строкой в `COMMON_DECISION.md` через
PR по ритуалу [D-008](COMMON_DECISION.md). Вердикт записать **любой**: отрицательный
результат здесь такой же результат, по [INTENTION.md](INTENTION.md) путь фиксируется честно,
включая тупики.
**Зависит от:** T-05, T-06, T-08, T-10а, T-12.

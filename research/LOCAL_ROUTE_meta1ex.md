## Это расходится с действующим решением

D-010 выбрал **OpenRouter единым транспортом**, а редакция 1 того же решения —
«локальная Gemma 4 12B» — стоит в отменённых с пометкой «отклонено до подписей».
Локальный маршрут возвращает ровно то плечо, которое было отклонено.

Ценой отказа там названа приватность: локальное плечо давало «фото не покидает
устройство». Довод в пользу возврата есть, но это **новое решение**, а не разведка:
по D-008 оно вносится PR'ом в `COMMON_DECISION.md` с approve второго участника.
Этот файл решением не является и в реестр не идёт.

## Что установлено твёрдо

**Модель картинки понимает.** `gemma-4-12B-it-qat-UD-Q4_K_XL.gguf` — файл из
[`unsloth/gemma-4-12B-it-qat-GGUF`](https://huggingface.co/unsloth/gemma-4-12B-it-qat-GGUF)
(имя `UD-Q4_K_XL` — их QAT-квант). Gemma 4 12B мультимодальна: текст, изображение, аудио.
То есть если картинка не пройдёт — дело будет в том, **как поднят сервер**, а не в модели.

**Vision в llama.cpp включается отдельным файлом.** Нужен мультимодальный проектор
(`mmproj`), он передаётся флагом `--mmproj` (он же `-mm`). Без него сервер поднимается
и отвечает, но изображение либо отбивается ошибкой, либо молча игнорируется — второе
опаснее: ответ по схеме придёт, и его легко принять за успех. В репозитории модели
проектор лежит: `mmproj-F16.gguf`, `mmproj-BF16.gguf`, `mmproj-F32.gguf`.

**Схемы llama-server держит, но форма другая, чем у OpenRouter.** Это главное расхождение
для T-03 (#12) и T-09 (#20):

| | OpenRouter | llama.cpp |
| --- | --- | --- |
| `response_format` | `{"type":"json_schema","json_schema":{"name":…,"strict":true,"schema":{…}}}` | `{"type":"json_schema","schema":{…}}` |

У llama.cpp поле `schema` **плоское**, без обёртки `json_schema` с `name`/`strict`. Один
и тот же объект в оба маршрута не отправить — если локальный путь останется опциональным,
форму придётся ветвить в коде.

Кодирование изображения при этом **совпадает**: тот же элемент `content` с data URL
`data:image/jpeg;base64,…`, как в основном рецепте. Здесь ветвить нечего.

## Почему проверка не состоялась

```
ping 192.168.1.38        → 0% потерь, 0.38 мс (хост живой, тот же /24)
tcp 192.168.1.38:8080    → connection refused
tcp 192.168.1.38:22,80,443,8000,11434,… → connection refused
tcp 192.168.1.1:80, :53  → open (TCP до LAN с этой машины работает)
```

Хост отвечает на ICMP и отвергает все проверенные TCP-порты, при том что до другого узла
той же сети TCP проходит. Сервер не запущен, либо слушает не тот интерфейс.

**Самая частая причина:** у `llama-server` адрес по умолчанию — `127.0.0.1:8080`, то есть
снаружи он не виден. Лечится флагом `--host 0.0.0.0`.

## Что сделать, чтобы маршрут заработал

Поднять сервер так, чтобы он был виден по сети **и** умел зрение:

```bash
llama-server \
  -m gemma-4-12B-it-qat-UD-Q4_K_XL.gguf \
  --mmproj mmproj-F16.gguf \
  --host 0.0.0.0 --port 8080 \
  -c 8192
```

- `--mmproj` — без него зрения нет; это и есть ответ на «а если картинки не понимает».
- `--host 0.0.0.0` — иначе `connection refused` снаружи, как сейчас.
- При запуске через `-hf` (скачивание с Hugging Face) проектор подтягивается сам, руками
  указывать не нужно; при локальном `-m` — нужно.
- `-c 8192` — контекст под картинку с запасом; значение не проверялось, подобрать по факту.

Проверить, что зрение действительно включилось, **до** прогона:

```bash
curl -s http://192.168.1.38:8080/props | jq .modalities
```

## Как проверить связку

Пробник лежит вне репозитория (код по D-003 идёт через PR, а эта задача — прямой push):
`scratchpad/local_probe.sh`, запуск `bash local_probe.sh 192.168.1.38:8080`.

Он проходит по шагам: доступность → что загружено и какие модальности → текст со схемой
в обеих формах `response_format` → изображение со схемой на двух фото.

Два фото взяты намеренно и не `item_10`/`item_13` (те зашиты в пункт 3 критерия D-011):

| фото | что в кадре | ожидаемо |
| --- | --- | --- |
| `item_15` | рамка-коллаж в пузырчатой плёнке на полу | 1 предмет, коричневый, в помещении |
| `item_03` | пять бокалов на подоконнике против света | 5 предметов, зелёный, в помещении |

Ответы должны **различаться**. Одинаковые или правдоподобные, но не про кадр — картинка
проигнорирована, и схема заполнена наугад. На OpenRouter эта же пара различила случаи
верно, так что сравнивать есть с чем.

Минимальный вызов руками:

```bash
B64=$(base64 -w0 input/item_03.jpg)
curl -s http://192.168.1.38:8080/v1/chat/completions -H "Content-Type: application/json" \
  -d "$(cat <<JSON
{
  "model": "gemma-4-12B-it-qat-UD-Q4_K_XL.gguf",
  "temperature": 0, "max_tokens": 300,
  "messages": [{ "role": "user", "content": [
    { "type": "text", "text": "Опиши это изображение по схеме. Отвечай только про то, что видно в кадре." },
    { "type": "image_url", "image_url": { "url": "data:image/jpeg;base64,$B64" } } ] }],
  "response_format": { "type": "json_schema",
    "schema": { "type": "object",
      "properties": {
        "dominant_color": { "type": "string" },
        "object_count":   { "type": "integer" },
        "is_indoor":      { "type": "boolean" } },
      "required": ["dominant_color","object_count","is_indoor"],
      "additionalProperties": false } }
}
JSON
)" | jq -r '.choices[0].message.content'
```

Ключ и `Authorization` не нужны — сервер локальный.
